01

XML Structure in Odoo

What is XML?

XML (eXtensible Markup Language) is a text format for structured data. It looks similar to HTML but with custom tag names. Odoo uses XML to define:

  • Views — how data appears (forms, lists, kanban)
  • Actions — what happens when you click a menu
  • Menus — the navigation sidebar
  • Data records — demo data, sequences, email templates
  • Security rules — record rules (ir.rule)

Basic XML Rules

XML Basics 
<?xml version="1.0" encoding="utf-8"?>
<!-- This is a comment -->
<odoo>
    <!-- All Odoo XML data goes inside <odoo> tags -->

    <!-- Every tag that opens must close -->
    <field name="value">Content</field>

    <!-- Self-closing tags (no content) -->
    <field name="check_date"/>

    <!-- Attributes go inside the opening tag -->
    <field name="state" widget="statusbar"/>
</odoo>

The <record> Tag — Heart of Odoo XML

Almost everything in Odoo XML uses the <record> tag. It creates or updates a record in the database.

Record Structure 
<record id="unique_xml_id" model="ir.ui.view">
    <field name="name">my.model.form</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
        <!-- The actual view definition goes here -->
    </field>
</record>
id Unique identifier (XML ID). Used to reference this record from other places. Convention: view_modelname_viewtype
model Database model to create record in. For views it is always ir.ui.view
name Human-readable name. Convention: model.name.viewtype
arch Short for "architecture". Contains the actual XML structure of the view

How Odoo Loads XML Files

XML files are loaded through __manifest__.py:

__manifest__.py 
# __manifest__.py
{
    'name': "Quality Control",
    'depends': ['stock'],
    'data': [
        'security/ir.model.access.csv',   # loaded first (security)
        'views/quality_check_views.xml',   # then views
        'views/menu.xml',                  # then menus
    ],
}
Order matters! Security files must come before views. Menu files referencing actions must come after the action is defined. If Odoo can't find an XML ID, it means the file defining it hasn't been loaded yet.

02

View Types

Odoo supports several view types. Each displays the same data differently. The view_mode field in the action decides which views are available.

📋

List (Tree)

Table of records with columns. Best for scanning many records.

📝

Form

Detailed single-record view for creating/editing.

📊

Kanban

Card-based view. Drag-and-drop between columns.

🔍

Search

Defines search filters, group-by options. Not a display view.

📅

Calendar

Date-based view. Shows records on a calendar grid.

List View

List view (historically called "tree") shows records as rows in a table. In Odoo 19 CE, use the <list> tag (not <tree> — that's deprecated).

Generic Example

Basic List View 
<record id="view_my_model_list" model="ir.ui.view">
    <field name="name">my.model.list</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
        <list string="My Records">
            <field name="name"/>
            <field name="date_field"/>
            <field name="state" widget="badge"
                decoration-success="state == 'done'"
                decoration-info="state == 'draft'"/>
        </list>
    </field>
</record>

Form View

Form view shows a single record for detailed viewing/editing. It has a specific structure: header → sheet → groups → notebook.

Form View Anatomy

Form View Structure 
<form string="My Record">
    <!-- 1. HEADER: Buttons + Status Bar -->
    <header>
        <button name="action_confirm" string="Confirm"
                type="object" class="btn-primary"
                invisible="state != 'draft'"/>
        <field name="state" widget="statusbar"
               statusbar_visible="draft,confirmed,done"/>
    </header>

    <!-- 2. SHEET: Main content area -->
    <sheet>
        <!-- Title area -->
        <div class="oe_title">
            <h1><field name="name"/></h1>
        </div>

        <!-- 3. GROUPS: Two-column layout -->
        <group>
            <group string="Left Column">
                <field name="field_a"/>
                <field name="field_b"/>
            </group>
            <group string="Right Column">
                <field name="field_c"/>
                <field name="field_d"/>
            </group>
        </group>

        <!-- 4. NOTEBOOK: Tabbed sections -->
        <notebook>
            <page string="Tab 1" name="tab_one">
                <field name="line_ids">
                    <list editable="bottom">
                        <field name="product_id"/>
                        <field name="quantity"/>
                    </list>
                </field>
            </page>
            <page string="Tab 2" name="tab_two">
                <field name="notes"/>
            </page>
        </notebook>
    </sheet>

    <!-- 5. CHATTER: Messages & activity log -->
    <chatter/>
</form>

Key Form Elements

ElementPurposeNotes
<header>Action buttons + status barAlways at top of form
<sheet>White card containing form fieldsRequired wrapper for fields
<group>Creates column layoutNested groups create 2-col layout
<notebook>Tab containerEach <page> is a tab
<chatter/>Message log + followersModel needs mail.thread mixin
class="oe_title"Large title stylingWrap <h1> with record name
invisibleConditionally hide elementsOdoo 19: use Python expression, not attrs
Odoo 19 Change! In Odoo 17+, attrs is removed. Use invisible="condition", readonly="condition", required="condition" directly.

Old (Odoo 16): attrs="{'invisible': [('state', '!=', 'draft')]}"
New (Odoo 19): invisible="state != 'draft'"

Kanban View

Kanban views display records as cards. They use QWeb templates inside the XML. This is where XML meets dynamic rendering.

Kanban Structure

Kanban View Anatomy 
<record id="view_my_model_kanban" model="ir.ui.view">
    <field name="name">my.model.kanban</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
        <kanban class="o_kanban_mobile">
            <!-- 1. Declare fields needed in template -->
            <field name="name"/>
            <field name="state"/>

            <!-- 2. QWeb template for each card -->
            <templates>
                <t t-name="card">
                    <div class="d-flex justify-content-between mb-2">
                        <field name="name" class="fw-bold"/>
                        <field name="state" widget="badge"/>
                    </div>
                    <div class="text-muted">
                        <field name="date_field"/>
                    </div>
                </t>
            </templates>
        </kanban>
    </field>
</record>

Kanban Key Concepts

ConceptExplanation
t-name="card"Odoo 19 uses card as template name (older versions used kanban-box)
default_group_byGroup cards into columns: default_group_by="state"
quick_createAllow quick-add cards: quick_create="false" to disable
progressbarShows progress bar per column for status tracking
Bootstrap CSSUse Bootstrap classes (d-flex, fw-bold, text-muted) for card layout

Odoo 19 CE Example (from sale module)

Sale Order Kanban (simplified) 
<kanban class="o_kanban_mobile" sample="1" quick_create="false">
    <field name="currency_id"/>
    <templates>
        <t t-name="card">
            <div class="d-flex align-items-baseline mb-2">
                <field name="partner_id" class="fw-bolder fs-5 me-2"/>
                <field name="amount_total" widget="monetary"
                       class="fw-bolder ms-auto"/>
            </div>
            <footer class="align-items-end">
                <div class="d-flex flex-wrap gap-1 text-muted">
                    <field name="name"/>
                    <field name="date_order"/>
                </div>
                <field name="state" widget="label_selection"
                    options="{'classes': {'draft': 'info',
                              'sale': 'success'}}"/>
            </footer>
        </t>
    </templates>
</kanban>

Search View

Search views don't display records. They define what search fields, filters, and group-by options appear in the search bar above list/kanban views.

Search View Structure

Search View Anatomy 
<record id="view_my_model_search" model="ir.ui.view">
    <field name="name">my.model.search</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
        <search string="Search My Model">
            <!-- 1. Search fields (type-ahead search) -->
            <field name="name" string="Reference"/>
            <field name="partner_id" operator="child_of"/>

            <!-- 2. Filters (predefined filter buttons) -->
            <separator/>
            <filter name="filter_draft" string="Draft"
                    domain="[('state', '=', 'draft')]"/>
            <filter name="filter_done" string="Done"
                    domain="[('state', '=', 'done')]"/>

            <!-- 3. Group By (in a group tag) -->
            <group>
                <filter name="group_by_state" string="Status"
                        context="{'group_by': 'state'}"/>
                <filter name="group_by_date" string="Date"
                        context="{'group_by': 'date_field'}"/>
            </group>
        </search>
    </field>
</record>

Key Concepts

ElementPurposeExample
<field>Searchable field (autocomplete)<field name="name"/>
<filter>Predefined filter buttondomain="[('state','=','draft')]"
<separator/>Visual separator between filtersGroups related filters
<group>Group-by sectionUses context={'group_by': 'field'}
filter_domainCustom search logicSearch across multiple fields

Calendar View

Calendar view displays records on a calendar based on a date field. Great for scheduling and timeline visibility.

Calendar View Structure

Calendar View 
<record id="view_my_model_calendar" model="ir.ui.view">
    <field name="name">my.model.calendar</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
        <calendar string="My Calendar"
                  date_start="start_date"
                  date_stop="end_date"
                  color="state"
                  mode="month"
                  quick_create="0">
            <field name="name"/>
            <field name="partner_id" avatar_field="avatar_128"/>
            <field name="state" filters="1" invisible="1"/>
        </calendar>
    </field>
</record>
AttributePurpose
date_startField for event start date (required)
date_stopField for event end date (optional — single-day if omitted)
colorField to color-code events
modeDefault view: month, week, or day
quick_createSet to 0 to disable click-to-create

03

Customization — Inheritance & XPath

One of Odoo's most powerful features: modify existing views without editing the original file. This is how custom modules extend base Odoo.

Why Inheritance?

Golden Rule: Never modify base Odoo source files. Always create a new module that inherits and extends. This way, your changes survive Odoo upgrades.

View Inheritance Basics

Inherited View Structure 
<record id="view_partner_form_inherit_my_module" model="ir.ui.view">
    <field name="name">res.partner.form.inherit.my_module</field>
    <field name="model">res.partner</field>
    <!-- Key: reference the original view -->
    <field name="inherit_id" ref="base.view_partner_form"/>
    <field name="arch" type="xml">
        <!-- Your modifications go here -->
    </field>
</record>

Position Attributes

Use position to tell Odoo where to place your changes:

PositionWhat it doesExample
afterAdd content after the matched elementAdd field after another field
beforeAdd content before the matched elementAdd button before existing button
insideAdd content inside the matched element (at end)Add fields to a group
replaceReplace the matched element entirelySwap one field for another
attributesModify attributes of the matched elementChange string, invisible, etc.

Method 1: Simple Field Matching

Simple Matching — Add after a field 
<!-- Find the 'phone' field and add our field after it -->
<field name="phone" position="after">
    <field name="my_custom_field"/>
</field>

<!-- Change attributes of existing field -->
<field name="email" position="attributes">
    <attribute name="required">1</attribute>
    <attribute name="string">Business Email</attribute>
</field>

<!-- Replace a field with something else -->
<field name="old_field" position="replace">
    <field name="new_better_field"/>
</field>

<!-- Add field inside a group -->
<group name="sale_info" position="inside">
    <field name="my_extra_field"/>
</group>

Method 2: XPath — Precise Targeting

When simple field matching won't work (field appears multiple times, or you need to target a <group>, <page>, or <div>), use XPath:

XPath Examples 
<!-- Target a specific notebook page by name attribute -->
<xpath expr="//page[@name='other_information']" position="after">
    <page string="Custom Tab" name="custom_tab">
        <field name="custom_notes"/>
    </page>
</xpath>

<!-- Target a div by class -->
<xpath expr="//div[@class='oe_title']" position="inside">
    <h3>Subtitle: <field name="subtitle_field"/></h3>
</xpath>

<!-- Target first group inside sheet -->
<xpath expr="//sheet/group[1]" position="after">
    <group string="Extra Info">
        <field name="extra_info"/>
    </group>
</xpath>

<!-- Target button by name -->
<xpath expr="//button[@name='action_confirm']" position="before">
    <button name="action_pre_check" string="Pre-Check"
            type="object"/>
</xpath>

Common XPath Expressions

XPathMatches
//field[@name='phone']Any field with name="phone"
//page[@name='tab_one']Notebook page with name="tab_one"
//group[@string='Sales']Group with title "Sales"
//sheet/group[1]First group directly inside sheet
//notebookThe notebook element
//header/button[1]First button in header

Real-World Odoo 19 CE Inheritance Example

From sale/views/sale_order_views.xml — how Sale module inherits its own base list view:

Odoo 19 CE: View Inheritance (sale module) 
<!-- Quotation list inherits from sale order list -->
<record id="view_quotation_tree" model="ir.ui.view">
    <field name="name">sale.order.list (quotes)</field>
    <field name="model">sale.order</field>
    <field name="inherit_id" ref="sale_order_tree"/>
    <field name="mode">primary</field>
    <field name="arch" type="xml">
        <!-- Change the title -->
        <list position="attributes">
            <attribute name="string">Quotations</attribute>
        </list>
        <!-- Replace date_order with create_date -->
        <field name="date_order" position="replace">
            <field name="create_date" string="Creation Date"
                   optional="show"/>

QWeb — Templates & Dynamic Rendering

QWeb is Odoo's template engine. It uses special t-* attributes in XML to create dynamic content. You already saw it in Kanban cards. It is also used for PDF reports and website pages.

QWeb Directives

DirectivePurposeExample
t-if Conditional rendering <span t-if="record.result.raw_value == 'pass'">✅</span>
t-else Else branch <span t-else="">❌</span>
t-elif Else-if branch <span t-elif="condition">...</span>
t-foreach Loop over items <t t-foreach="lines" t-as="line">...</t>
t-esc Output escaped text <span t-esc="record.name.value"/>
t-out Output (Odoo 17+, replaces t-esc in reports) <span t-out="doc.name"/>
t-att-* Dynamic attribute <div t-att-class="'bg-' + color"/>
t-set Set a variable <t t-set="total" t-value="100"/>
t-call Include another template <t t-call="web.html_container"/>

Bonus Tips & Common Pitfalls

Odoo 19 CE Specific Changes

❌ attrs is Dead

attrs="{'invisible': [...]}" no longer works in Odoo 17+. Use invisible="python_expression" directly.

📋 <list> not <tree>

<tree> still works but is deprecated. Use <list> tag in new code.

🎴 t-name="card"

Kanban template name changed from kanban-box to card in newer Odoo versions.

📤 t-out over t-esc

In reports, prefer t-out (Odoo 17+) over t-esc. Both work but t-out is the modern way.

🏷️ column_invisible

To hide columns conditionally in list view, use column_invisible instead of invisible (which hides the cell, not the column).

🔑 Always Use name=

Give name attributes to <page>, <group>, etc. Makes inheritance targeting much easier.

Business Logic (ORM Methods)

Odoo's Object-Relational Mapping (ORM) framework gives us powerful Python decorators to handle dynamic business rules. The core decorators you will use frequently are @api.depends, @api.onchange, and @api.constrains.

Understanding self: In Odoo ORM methods, self represents a Recordset (a collection of records). It is not just a single record! Always use a for record in self: loop when computing or constraining values to avoid ValueError: Expected singleton errors.

1. Computed Fields & Onchange

What is the difference between them?

  • Computed Fields (@api.depends): Used to calculate a field's value dynamically based on other fields. If store=True is set, the value is saved to the database. If not, it is computed on-the-fly every time the record is loaded.
  • Onchange (@api.onchange): Triggers immediately in the user interface before saving to the database. It is primarily used to return warnings, update domains, or pre-fill fields when a user types.
quality_control_line.py 
    # The field definition must include the compute method name
    remain_qty = fields.Float('Remain Qty', compute='_compute_remain_qty', store=True)

    @api.depends('rec_qty', 'damage_qty')
    def _compute_remain_qty(self):
        for line in self:
            line.remain_qty = line.rec_qty - line.damage_qty

    @api.onchange('damage_qty', 'rec_qty')
    def _onchange_damage_qty(self):
        # Triggers in the browser as the user types
        if self.damage_qty > self.rec_qty:
            return {
                'warning': {
                    'title': 'Invalid Quantity', 
                    'message': 'Damage cannot exceed Received Quantity.'
                }
            }

2. Data Validation: Python vs SQL Constraints

When you need to ensure data integrity, you have two options:

  • _sql_constraints: Executed directly by the PostgreSQL database. Extremely fast and prevents duplicate names or standard data checks.
  • @api.constrains: Executed by Python. Slower, but allows for complex conditional logic, API calls, or date comparisons that SQL cannot easily do.
quality_control.py 
    # 1. SQL Constraint: Enforced by PostgreSQL
    _sql_constraints = [
        ('name_uniq', 'unique (name)', 'The Reference Name must be unique!')
    ]

    # 2. Python Constraint: Enforced by Odoo ORM
    @api.constrains('check_date')
    def _check_date(self):
        for record in self:
            # Complex check using Python libraries
            if record.check_date > fields.Date.today():
                raise ValidationError("Check date cannot be in the future.")
