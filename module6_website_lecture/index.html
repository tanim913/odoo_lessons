Website Basics & Module Structure

Before writing a single line of website code, you need to understand the three core modules that power Odoo's web layer. They live in /odoo/odoo19-server/addons/ and build on top of each other.

The Three Pillars

Module Path Purpose Key Dependencies
web addons/web/ Core HTTP framework. Provides the request/response cycle, assets bundling, RPC layer, and the backend JavaScript framework. Every Odoo module depends on this implicitly. None (base framework)
website addons/website/ The website builder. Adds website.layout template, routing with website=True, SEO tools, themes, multi-website support, and the drag-and-drop page editor. portal, web, http_routing, mail, auth_signup
website_sale addons/website_sale/ eCommerce layer. Product catalog, cart, checkout, payment integration. Built entirely on top of website and sale. website, sale, payment
Dependency Chain: web is the foundation that everything relies on. website adds the public-facing layer. website_sale adds commerce. When you depend on website, you automatically get portal (customer dashboard), http_routing (slug URLs), and more.

What portal Provides

The portal module (at addons/portal/) gives us:

  • The /my/home customer dashboard with card-based navigation
  • The CustomerPortal controller class we can inherit
  • Portal templates: portal.portal_layout, portal.portal_searchbar, portal.portal_table
  • Pager utility for paginated lists
  • Login/signup flow via auth_signup

Controllers — @http.route

Controllers are the C in MVC. They map URLs to Python functions. In Odoo, every controller is a class that extends http.Controller (or CustomerPortal for portal pages).

1. The @http.route Decorator — Deep Dive

Every parameter in @http.route controls how Odoo handles the incoming request:

route='/my/path' The URL endpoint. Can be a string or a list: ['/path', '/path/page/<int:page>']
type='http' Request type. 'http' = standard page. 'json' / 'jsonrpc' = AJAX/RPC calls returning JSON.
auth='public' Authentication level. Controls who can access this route. See details below.
website=True Renders within the website context (applies themes, languages, menus, header/footer).
methods=['POST'] Restricts to specific HTTP methods. Default is ['GET', 'POST'].
sitemap=False Excludes this route from the sitemap.xml that search engines crawl.

2. Authentication Levels Explained

The auth parameter determines who can access your route:

auth Value Who Can Access request.env.user Use Case
'public' Everyone (logged in or not) Public user (guest) or actual user Public website pages, contact forms
'user' Logged-in users only (portal + internal) The actual logged-in user Portal pages like /my/applications
'none' Framework level — no user/database context N/A Health checks, static assets, special endpoints

3. Base Code Example: How sale Inherits Portal

The sale module shows the standard pattern. Its controller at addons/sale/controllers/portal.py inherits CustomerPortal:

Base Code: addons/sale/controllers/portal.py (simplified) 
from odoo.addons.portal.controllers.portal import CustomerPortal, pager as portal_pager

class CustomerPortal(CustomerPortal):

    def _prepare_home_portal_values(self, counters):
        """Add sales order count to portal home dashboard."""
        values = super()._prepare_home_portal_values(counters)
        partner = request.env.user.partner_id
        SaleOrder = request.env['sale.order']

        if 'order_count' in counters:
            values['order_count'] = (
                SaleOrder.search_count(self._prepare_orders_domain(partner))
                if SaleOrder.has_access('read') else 0
            )
        return values

    @http.route(['/my/orders', '/my/orders/page/<int:page>'],
                type='http', auth='user', website=True)
    def portal_my_orders(self, **kwargs):
        """Render the list of sales orders."""
        values = self._prepare_sale_portal_rendering_values(**kwargs)
        return request.render("sale.portal_my_orders", values)
Key Pattern: Every portal module follows this exact structure:
  • Inherit CustomerPortal
  • Override _prepare_home_portal_values to add your counter
  • Add routes with auth='user' for portal pages
  • Use portal_pager for pagination

4. Our quality_control Controllers

We create two controller classes: one for public website pages, one for portal.

Public Website Controller

quality_control/controllers/controllers.py — Website Part 
from odoo import http
from odoo.http import request

class QualityControlWebsite(http.Controller):
    """Public website controllers — anyone can access these."""

    @http.route('/quality/checks', type='http', auth='public', website=True)
    def quality_checks_page(self, **kw):
        """Public page showing quality checks.
        Demonstrates: qcontext dict passing to templates."""
        checks = request.env['quality.check'].sudo().search([], limit=20)
        # qcontext: every key becomes a variable in the QWeb template
        qcontext = {
            'checks': checks,
            'page_title': 'Quality Checks Overview',
            'company_name': request.env.company.name,
        }
        return request.render('quality_control.quality_checks_page_template', qcontext)

    @http.route('/jobs/apply', type='http', auth='public', website=True)
    def job_application_form(self, **kw):
        """Render the job application form with position choices."""
        positions = [
            ('qa_inspector', 'QA Inspector'),
            ('qa_engineer', 'QA Engineer'),
            ('qa_lead', 'QA Lead'),
        ]
        return request.render('quality_control.job_application_form_template', {
            'positions': positions,   # passed to template as qcontext
        })

    @http.route('/jobs/submit', type='http', auth='public',
                website=True, methods=['POST'])
    def job_application_submit(self, **post):
        """Handle form submission."""
        import base64
        resume_file = post.get('resume')
        resume_base64 = base64.b64encode(resume_file.read()) if resume_file else False

        vals = {
            'name': post.get('name'),
            'email': post.get('email'),
            'phone': post.get('phone'),
            'position': post.get('position', 'qa_inspector'),
            'cover_letter': post.get('cover_letter'),
            'resume': resume_base64,
            'resume_name': resume_file.filename if resume_file else False,
        }

        # Link partner for logged-in users (portal users)
        if not request.env.user._is_public():
            vals['partner_id'] = request.env.user.partner_id.id

        # sudo() needed — public users have no write access
        application = request.env['quality.job.application'].sudo().create(vals)

        return request.render('quality_control.job_application_success_template', {
            'name': application.name,
            'email': application.email,
        })

Portal Controller (following sale module pattern)

quality_control/controllers/controllers.py — Portal Part 
from odoo.addons.portal.controllers.portal import CustomerPortal, pager as portal_pager

class PortalJobApplication(CustomerPortal):
    """Portal controllers — same pattern as sale module."""

    def _prepare_home_portal_values(self, counters):
        """Add job application count to portal dashboard."""
        values = super()._prepare_home_portal_values(counters)
        if 'job_application_count' in counters:
            JobApp = request.env['quality.job.application']
            values['job_application_count'] = (
                JobApp.search_count([])      # ir.rule auto-filters!
                if JobApp.has_access('read')
                else 0
            )
        return values

    @http.route(['/my/applications', '/my/applications/page/<int:page>'],
                type='http', auth='user', website=True)
    def portal_my_applications(self, page=1, sortby=None, **kwargs):
        """List applications. Portal sees own, Internal sees all."""
        JobApp = request.env['quality.job.application']
        values = self._prepare_portal_layout_values()

        searchbar_sortings = {
            'date': {'label': 'Newest', 'order': 'create_date desc'},
            'name': {'label': 'Name', 'order': 'name asc'},
            'state': {'label': 'Status', 'order': 'state asc'},
        }
        sortby = sortby or 'date'

        application_count = JobApp.search_count([])
        pager = portal_pager(
            url='/my/applications',
            total=application_count,
            page=page,
            step=self._items_per_page,
        )
        applications = JobApp.search(
            [], order=searchbar_sortings[sortby]['order'],
            limit=self._items_per_page, offset=pager['offset'],
        )

        values.update({
            'applications': applications,
            'page_name': 'my_applications',
            'pager': pager,
            'default_url': '/my/applications',
            'sortby': sortby,
            'searchbar_sortings': searchbar_sortings,
        })
        return request.render('quality_control.portal_my_applications', values)
Why sudo()? When auth='public', the user is a guest with no database permissions. To write to a model, you must use .sudo(). But for portal routes (auth='user'), the logged-in user's permissions + record rules handle access — no sudo() needed.

QWeb Templates for Website

QWeb is Odoo's template engine. Controllers pass data to templates via a qcontext dict, and QWeb renders HTML using t- prefixed directives.

1. The qcontext Flow

How Data Flows:
  1. Controller builds a Python dict (qcontext)
  2. Controller calls request.render('template_xml_id', qcontext)
  3. QWeb engine receives the dict — every key becomes a template variable
  4. Template uses t-esc, t-foreach, etc. to render the data
Controller (Python) 
# The dict passed to request.render() IS the qcontext
qcontext = {
    'checks': checks,                     # recordset
    'page_title': 'Quality Checks',       # string
    'company_name': request.env.company.name,  # string
}
return request.render('quality_control.quality_checks_page_template', qcontext)

2. QWeb Directive Reference

Directive Purpose Example
t-esc="var" Output variable (HTML-escaped, safe from XSS) <span t-esc="name"/>
t-out="var" Output variable (same as t-esc in Odoo 17+) <t t-out="count"/>
t-field="record.field" Render field with proper widget (dates, monetary, etc.) <span t-field="app.state"/>
t-if / t-elif / t-else Conditional rendering <t t-if="not records">...</t>
t-foreach / t-as Loop through lists or recordsets <t t-foreach="checks" t-as="check">
t-att-* Dynamic attribute (evaluated Python expression) <div t-att-class="'active' if x else ''">
t-attf-* Format string attribute (mix static + dynamic) <a t-attf-href="/order/#{order.id}">
t-call="template_id" Include another template (like a partial) <t t-call="website.layout">
t-set / t-value Set a variable inside the template <t t-set="title">My Page</t>

3. Layout Templates

Two main layout templates you'll use:

Template When to Use What It Provides
website.layout Public website pages (anyone can see) Full website header, footer, navigation, theme, SEO
portal.portal_layout Portal pages (logged-in users) Portal navbar, breadcrumbs, sidebar, user context

<template id="quality_checks_page_template" name="Quality Checks Page">

                                          else 'bg-danger' if check.result == 'fail'

5. Building a Form — Job Application

This template uses t-foreach on a Python list to render dropdown options dynamically:

quality_control/views/website_templates.xml — Job Form 
<template id="job_application_form_template" name="Job Application Form">
    <t t-call="website.layout">
        <div id="wrap" class="container mt-5 mb-5">
            <form action="/jobs/submit" method="post" enctype="multipart/form-data">
                <!-- CRITICAL: csrf_token prevents Cross-Site Request Forgery -->
                <input type="hidden" name="csrf_token"
                       t-att-value="request.csrf_token()"/>

                <!-- Standard form fields -->
                <input type="text" name="name" required="required"/>
                <input type="email" name="email" required="required"/>

                <!-- Dynamic dropdown from qcontext list -->
                <select name="position" required="required">
                    <t t-foreach="positions" t-as="pos">
                        <!-- t-att-value: sets the option value dynamically -->
                        <option t-att-value="pos[0]" t-esc="pos[1]"/>
                    </t>
                </select>

                <textarea name="cover_letter"/>
                <input type="file" name="resume" accept=".pdf"/>
                <button type="submit">Submit</button>
            </form>
        </div>
    </t>
</template>
Never forget csrf_token! Every POST form must include <input type="hidden" name="csrf_token" t-att-value="request.csrf_token()"/>. Without it, Odoo will reject the submission with a 400 Bad Request. This prevents Cross-Site Request Forgery attacks.
t-esc vs t-field vs t-out:
  • t-esc — Use for plain Python variables (strings, numbers). Escapes HTML.
  • t-field — Use for ORM record fields. Applies the proper widget (date formatting, monetary, badges, etc.).
  • t-out — Same as t-esc in Odoo 17+. Can output raw HTML if the variable is Markup.

Portal: Views & Security

The portal system lets external users (customers, applicants) log in and view their own data. Building a portal page requires both security configuration and template integration.

1. Three User Types in Odoo

Every user in Odoo belongs to one of these groups. Understanding this is critical for security:

User Type Group Can Log In? What They See Examples
Public base.group_public No Public website pages only Anonymous visitors, job applicants
Portal base.group_portal Yes Their own records via /my/ Customers, suppliers, applicants
Internal base.group_user Yes All records + backend Employees, HR staff, managers

2. Security Layer 1: Access Rights (ir.model.access.csv)

This file controls which operations each group can perform (Create, Read, Update, Delete):

quality_control/security/ir.model.access.csv 
id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
# Public: can only CREATE (submit forms). No read — controller uses sudo()
access_job_application_public,...,model_quality_job_application,base.group_public,0,0,1,0
# Portal: can READ only (ir.rule filters to own records)
access_job_application_portal,...,model_quality_job_application,base.group_portal,1,0,0,0
# Internal: full CRUD
access_job_application_user,...,model_quality_job_application,base.group_user,1,1,1,1
Why public read=0? Public users submit via sudo() in the controller. They never directly read records. If you set read=1, public users could potentially access data through crafted URLs.

3. Security Layer 2: Record Rules (ir.rule)

Access rights say what operations. Record rules say which records. They apply a domain filter at the database level:

quality_control/security/security.xml 
<data noupdate="1">
    <!-- PORTAL USERS: Only see their own applications -->
    <record id="job_application_portal_rule" model="ir.rule">
        <field name="name">Portal: own job applications only</field>
        <field name="model_id" ref="model_quality_job_application"/>
        <!-- domain_force filters at database level -->
        <field name="domain_force">[('partner_id', '=', user.partner_id.id)]</field>
        <field name="groups" eval="[(4, ref('base.group_portal'))]"/>
        <field name="perm_read" eval="1"/>
        <field name="perm_write" eval="0"/>
        <field name="perm_create" eval="0"/>
        <field name="perm_unlink" eval="0"/>
    </record>

    <!-- INTERNAL USERS: See ALL applications -->
    <record id="job_application_internal_rule" model="ir.rule">
        <field name="name">Internal: all job applications</field>
        <field name="model_id" ref="model_quality_job_application"/>
        <field name="domain_force">[(1, '=', 1)]</field>
        <field name="groups" eval="[(4, ref('base.group_user'))]"/>
    </record>
</data>
partner_id vs create_uid: We use partner_id instead of create_uid for portal filtering. Why? When a public (guest) user submits a form via sudo(), the create_uid is the system user — not the applicant. By storing partner_id explicitly, we link records to the right person even if they register as a portal user after submitting.

@http.route(['/my/applications/<int:application_id>'], type='http', auth="user", website=True)
def portal_my_application_detail(self, application_id, **kw):

5. How Record Rules Work in Practice

The Magic of search([]): Notice how the controller does JobApp.search([]) with an empty domain. It looks like it would return ALL records. But Odoo's record rules silently add the domain filter. For a portal user, search([]) becomes search([('partner_id', '=', current_user.partner_id.id)]) automatically. For an internal user, no filter is added — they see everything.

1. The Model

from odoo import api, fields, models

class QualityJobApplication(models.Model):
    _name = 'quality.job.application'
    _description = 'Quality Inspector Job Application'
    _order = 'create_date desc'

    name = fields.Char('Applicant Name', required=True)
    email = fields.Char('Email Address', required=True)
    phone = fields.Char('Phone Number')
    position = fields.Selection([
        ('qa_inspector', 'QA Inspector'),
        ('qa_engineer', 'QA Engineer'),
        ('qa_lead', 'QA Lead'),
    ], string='Position', default='qa_inspector')
    cover_letter = fields.Text('Cover Letter')
    state = fields.Selection([
        ('draft', 'Draft'),
        ('review', 'Under Review'),
        ('accepted', 'Accepted'),
        ('rejected', 'Rejected')
    ], string='Status', default='draft')

    resume = fields.Binary('Resume', attachment=True)
    resume_name = fields.Char('Resume File Name')

    # Link to partner for portal access filtering
    partner_id = fields.Many2one('res.partner', string='Applicant Partner', index=True)

    @api.model_create_multi
    def create(self, vals_list):
        """Auto-assign partner_id from logged-in user."""
        for vals in vals_list:
            if not vals.get('partner_id') and not self.env.user._is_public():
                vals['partner_id'] = self.env.user.partner_id.id
        return super().create(vals_list)

5. Common Pitfalls

Top Mistakes to Avoid:
  • Missing CSRF token: POST forms without csrf_token return 400 errors
  • Forgetting sudo(): Public users have no write permissions — always use sudo() for form submissions
  • Using create_uid for portal rules: When public users submit via sudo(), the create_uid is the system user, not the applicant
  • Missing enctype: File uploads require enctype="multipart/form-data" on the form tag
  • Wrong counter name: The placeholder_count in the template must exactly match the key in _prepare_home_portal_values
